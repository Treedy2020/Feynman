Rust 初版已实现 · 2026-10-08

一个 Agent，一条可恢复的消息通路。

当前演进目标是每个 Project 最多一个长期 Agent；用户通过 CLI 管理它的生命周期与权限。用户消息、Schedule 和外部事实源通知进入同一个持久收件箱。每个 Schedule 自己开窗、封窗并投递给一个固定 Agent，断线后可补查历史。

已实现用户管理的 Agent、独立事实源历史、Schedule 固定开窗、持久 Inbox 与原生 steer。每项目最多一个未归档 Agent、一个活跃 Run。新消息推荐使用 inbox send；旧 send / /messages 仍是立即启动的兼容入口，不提供 Inbox 排队。2026-10-09 新增 环境、租约与记忆；多 Agent、一对多投递仍是后续。本轮没有发起真实认证、模型分析或部署。

对象归属与关系不意味着
Project Agent本阶段项目内 0..1 个长期身份；拥有独立 Session / Conversation。必须存在一个特权 Main Agent。
Default AgentProject 可选的缺省消息路由目标。所有 Schedule 的动态目标或额外权限。
Project WorkspaceProject 拥有的持久文件系统及执行环境；不属于 Agent 会话。共享模型上下文、会话身份或凭证。
Project Schedule一个持久触发规则，创建时解析并固定一个目标 Agent ID。每次触发必定产生独立 Agent Run。
Occurrence / Delivery一个收集窗口形成一个 Occurrence，关联一条目标 Agent 的 Delivery。与用户消息使用不同的投递系统。
Agent Inbox Message用户、Schedule 或外部通知的持久输入；每条有稳定消息 ID 和来源。已经被模型读到或任务已经完成。
Schedule 模块

每个 Schedule 独立开窗，也能补查监听空窗。

时间型 Schedule 在指定时刻或间隔形成 Occurrence，例如每小时检查一次项目日志、每半天调查一次 bad cases。事件型 Schedule 由已获权的事实源变化触发，例如某人的 DWS 消息。它们共享投递机制；时间型可让 Agent 在收到消息后主动调用外部工具，事件型先由 Feynman 收集事件，再通知 Agent。

事件型的 collect_for_seconds 属于整个 Schedule，而不是每个人、群或匹配条件各开一个窗口。调度器首次看到符合规则的新记录时开窗，结束时间固定，不因后续事件延长。举例：10:00 首条消息开启 30 分钟窗口；10:05 和 10:28 的不同发件人消息都进入此窗；10:30 封窗形成一次 Occurrence；10:31 的事件进入下一窗口。持续聊天不会让唤醒无限推迟。仅消费 Schedule 创建后入库的新记录，已有历史可由 Agent 主动查询。

同一来源事件用稳定事件／消息 ID 去重；窗口、事件范围和已完成补查水位持久化。频繁变化时每个 Schedule 至多保留一个尚未开始投递的聚合通知，后续封窗的 Occurrence 关联到这条收件箱消息，并入待投递事实范围；每个 Occurrence 仍有独立 Delivery 供审计，但这批 Delivery 可由一次运行时接收确认共同完成。一旦开始投递就冻结消息快照，新事件进入下一条待投递通知。默认只通知「来源发生变化」、时间范围、数量与来源 ID；Agent 经授权按需读取正文。外部正文始终是未可信输入。

DWS 实时消息由本地 Feynman Server 托管长连接，精确绑定授权账号、群／人和规则，不能寄生在一次 Agent Run 中。Server 休眠或监听掉线时标记 gap；恢复后按用户允许的历史范围、源身份及时间区间发起补查，与实时流通过稳定消息 ID 去重。历史查询必须显式给出起止时间（半开区间 [start,end)）、翻完分页，并核对结果的完成／部分失败标记；只在完整补查后推进水位。无法覆盖的历史区间保持 partial 或 unknown，向 CLI 显示，不宣称零遗漏。已封窗的 Occurrence 不原地改写；迟到的历史事实形成带原始时间范围和补查来源的新 Occurrence。

当前区分 manual、dws_messages（有界历史采集）与 dws_events（真实长连接）。历史采集每次最多 24 小时，自动 poll 按最多一小时的段推进，仅完整结果推进游标；显式 backfill 保存范围留证，不自动改变连续游标。实时监听只接受稳定群 ID 或 open_dingtalk_id、精确 profile 和 message 事件，必须收到 ready，单次最多十分钟、最多十六个消费者，退出使用 SIGTERM。监听失败不盲重试；非正常重启标为 interrupted，可能尚存的消费者在 listener_until 到期后才允许所有者 resume。实时空窗的自动历史补查尚未实现，需显式 backfill；不能宣称零遗漏。gcloud 仍只是未来示例。

持久分区已实现规则
Source 注册实例每次 create 生成新 Source ID；同名、同账号、不同时间登记也不复用历史。固定 Project / Agent / Connection / 资源时间范围，扩大范围需新建。
Observation 历史独立 source_id + event_id 去重，保留 occurred_at / observed_at / sequence / 正文。重复 ID 保留首个快照；不做撤回、编辑的版本推断。
Capture 留证分页查询 poll / backfill 的起止范围、完成标记与监听停止；last_capture_complete 只表示最近一次范围，不表示全历史无缺口。
本地可发现所有者 CLI sources list / read / captures / watch 和 feed read / watch；Agent MCP feynman_observations 的 sources / query / captures / feed，仅查询其固定 Agent 的本地历史，不提供管理或取密钥操作。单渠道窗口与项目统一 Feed共享持久历史，但查看位置与本 Schedule 的水位独立。
投递模块

先持久化，再投递；确认接收不等于工作完成。

inbox send 的用户输入与 Schedule Occurrence 先成为 Agent Inbox Message，绑定固定 Agent ID 与稳定消息 ID。Occurrence 对同一 schedule + opened_at 唯一，并关联目标 Agent / Inbox；当前不另建重复的 Delivery 表，投递状态通过 Inbox 关联。多个未派发 Occurrence 共用一条聚合通知，包含全部窗口与事实 sequence 范围；开始派发后冻结，新事实进入下一条通知。旧的立即发送入口仍保留兼容行为。

投递消息是向目标 Agent 的长期会话追加一条新输入，不修改已有的「最后一条消息」。目标空闲时启动新 turn；运行中按该 Schedule 的投递策略排队或尝试 steer 当前 turn。例行巡检默认 queue；确需改变当前工作方向的通知才选 steer_if_active。根据 Codex App Server 官方文档，turn/steer 要求当前 thread 与 expectedTurnId 匹配，向活跃 turn 追加输入，不产生新的 turn/started；它属于现有 Run，不凭空新建 Run。若因 turn 恰好完成而拒绝 steer，该投递回到队列，由下一 turn 消费；已经确认接收的输入不重发。

状态含义下一步
pending收件箱已落盘，尚未调用运行时；也可因明确拒绝而等待退避重试。Agent 可用且轮到此消息时进入 dispatching。
dispatching数据库唯一约束保证同 Agent 一个派发者，已记录 Inbox ID，正在调用 turn/start 或 turn/steer。收到明确确认进 accepted；明确未接收回 pending；超时或进程崩溃进 unknown。
accepted运行时确认接收，关联记录 native thread / turn 的 Run ID；这是投递终态，不代表模型已处理或任务成功。Run 的完成／失败在独立执行记录中跟踪，不重发此消息。
unknown请求可能已被接收，但响应丢失；不能安全自动重发。先用消息 ID 与原生会话历史对账；证实已收则 accepted，证实未收才回 pending，无法判定则保留并提示用户。
cancelled用户明确取消未接收的消息，或归档目标 Agent；停用 Agent / Schedule 只暂停 pending，不删除。终态；已 accepted 的输入不可通过取消撤回。

状态变化落盘，审计仅保存身份、动作、对象 ID 与时间。进程重启将未确认的 dispatching 转 unknown，不自动重放；当前由所有者查看 Run / 原生历史后通过 CLI reconcile，尚无自动对账器。unknown 阻塞同 Agent 后续投递。waiting_approval 时排队；只有确认活跃 turn 才尝试 steer，明确拒绝回 pending。accepted 不重发，不承诺端到端 exactly-once。

Agent 注册模块

Agent 的生灭和权限属于用户，不属于 Agent 自己。

使用 projects create --without-agent 可先准备项目与 Workspace；最多一个未归档 Agent。用户可 CRUD、启停、授予／撤销能力，用完整 update JSON 改默认路由。未指定 --agent 时必须有默认 Agent；Schedule 创建时固定 Agent ID，变更默认值或创建替代身份不会改派旧 Schedule。创建时登记稳定身份，首次运行时才准备 Session / Conversation / 原生 thread。

生命周期为 active → disabled → archived，disabled 可恢复。停用或收紧权限立即阻止新调用与监听／投递，不强杀已经运行的模型或应用进程。delete 归档，保留历史并取消 pending；必须先结束活跃 Run、处理 unknown / dispatching。归档后不可复活，替代 Agent 使用新 ID、新 Session / Conversation，不继承旧来源或能力。迁移保留旧会话，并在迁移时固定旧 Schedule 目标。MCP 不提供所有者管理操作；同一 OS 用户仍不构成强安全隔离。

多 Agent 属于未来扩展：Project 可容纳多个长期 Agent、各有 Session / Conversation，共用项目 Workspace；届时需解决并发写入（独立 Git worktree 或写入租约）和隔离级别。Reviewer、Agent 间消息、跨 Agent 改派与一对多 Schedule 均仅预留模型，不进入单 Agent MVP。

External Access 与安全

权限由用户授予、撤销，并在每次调用时复核。

认证 Connection、Project Binding 和业务 Tool Grant 继续分开。用户通过 CLI 管理 Agent 的可用能力与审批策略；运行时校验至少包含 tenant + project + agent + action + resource，不能因为项目只有一个 Agent 就跳过 Agent 身份。Agent 可发起权限申请，但不能自行批准、扩大或恢复被撤销的授权。Schedule 的创建／启用、监听范围和历史补查范围同样需要用户控制。DWS 消息、日志等外部事实不能授予新权限或作为系统级指令。

已实现 Project Tool Grant 与 Agent capability allowlist 的交集，再复核 Connection、Binding 到期和 DWS 精确资源／时间 Scope。兼容创建的默认 Main Agent 与迁移身份以 capabilities=null 沿用项目 Grant；首次所有者修改会冻结为显式列表。agents create 的新身份 capabilities=[]，需明确授予能力，仍不能替代项目 Grant。当前外部工具保持只读，没有对外发消息或部署接口。

已实现的事实流见 ObservationSource / Subscription：采集、补查、入箱、投递与 DWS 历史查询各自复核权限；撤权后保留记录但暂停后续使用。Project Memory 已追加证据关联的结构化判断与待办；任务执行仍走现有队列，物理保留清理待实现。

初版实现与剩余边界

单 Agent 的闭环已落地，生产安全能力分阶段实现。

  1. 已实现：旧身份／Session／Conversation 迁移、Agent CRUD 与权限交集、无 Agent 项目、来源实例持久分区与 Agent 只读查询。
  2. 已实现：单 Agent 固定目标、整个 Schedule 固定开窗、待投递聚合、事务化 Occurrence / Inbox、queue / steer、重启 unknown 与所有者对账。
  3. 已实现：DWS 稳定目标真实监听、授权和范围检查、SIGTERM 清理、有界历史采集与补查、部分结果留证及不推进游标。离线公开接口测试见 集成测试；迁移／隔离／恢复测试见 Rust 测试。
  4. 已追加：通用 MemoryStore、环境 Profile 与指定进程装载、凭证版本和使用租约，见 当前实现契约。未实现：实时空窗自动补查、自动原生历史对账、物理保留清理、多 Agent / 广播、Provider 真正短期签发与远程多用户认证。强租户隔离不在当前个人版范围，不对外托管不可信租户。

模块边界：Schedule 负责「何时产生 Occurrence、事实窗口是否完整」，收件箱／投递负责「何时交给 Agent 以及如何恢复」，Agent 注册负责身份与生命周期，External Access 负责有效授权。Codex App Server 只是运行时适配，不把原生 turn ID 当作 Feynman 长期身份。这些对象在 可视化工作台中通过同一 Rust Server 查询和操作。
